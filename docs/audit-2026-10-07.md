# Audit sécurité & propreté — 2026-10-07

Audit en lecture seule de tout le dépôt (contrats, ticketd, shared, launcher
Rust + TS, web), puis correctifs « rapides » appliqués le jour même. Chaque
constat a été vérifié dans le code ; les critiques ont été re-vérifiés à la
main avant correction.

Légende : ✅ corrigé · 🟡 atténué (correctif partiel) · ⏳ à faire (structurel / décision produit)

## Les 5 risques majeurs

| # | Risque | Statut |
|---|---|---|
| T1 | **Clé de jeu détournable** : n'importe qui crée une édition à 0 ETH pointant le CID d'un autre studio et obtient la clé de contenu | ✅ `/publish` signé par le wallet du studio (empreinte du fichier + n° de studio vérifié on-chain) ; la clé n'est libérée que pour les éditions **de ce studio**, et un CID appartient à la première édition qui l'enregistre |
| L1 | **Clé plateforme DEV (publique) acceptée** par le launcher → tickets forgeables | ✅ acceptée uniquement en `vite dev`, jamais dans un build de release |
| L2 | **Carte SD piégée → XSS → exécution de code** (tokenId non échappé, CSP absente, `withGlobalTauri`) | ✅ schéma du ticket/meta validé dans `judge()`, échappement, CSP stricte, `withGlobalTauri: false`, ouverture d'URL limitée au store ; côté Rust : volumes limités à ceux détectés, tokenId numérique |
| T2-T3 | **ticketd ouvert sur le réseau**, endpoints sans authentification (`backdate`, `publish`) | ✅ écoute en boucle locale uniquement (IPv4 + IPv6), CORS en liste blanche, corps plafonnés, `backdate` seulement en mode dev (`npm run dev`), `/publish` signé par un studio |
| T4 / K1 | **Licence jouable sur N machines** ; **une seule clé** pour tout (déployeur, frais, attestations, tickets) | ✅ K1 : clés séparées (tickets / attestations rotatable / admin + frais), l'ancienne clé fuitée n'a plus aucun rôle. ⏳ T4 registre d'appareils ; ⏳ régénérer le JWT Pinata (action Pinata) |
