Architecture technique GameVault

Comment le système est construit, où vivent les données et les clés, comment les pièces se parlent, et comment on le déploie, du poste de développement au cluster Kubernetes.

Comment lire ce document

Les sections 1 à 3 donnent le modèle : principes, composants, vue d'ensemble. La section 4 décrit les trois façons de faire tourner la plateforme. Les sections 5 à 7 détaillent les données, les clés et les flux, avec le fichier où se trouve le code. La section 8 est une référence à consulter. Les sections 9 à 11 disent ce qui est garanti, comment on vérifie, et ce qui reste à faire.

Le parcours utilisateur, les écrans et les règles métier sont dans le document compagnon : Dossier fonctionnel GameVault. L'exploitation au quotidien est dans docs/runbook.md.

Une pastille indique qui agit : joueurstudiolaunchersiteticketdblockchain. Les chemins sont relatifs à la racine du dépôt.

1. Principes

Le support transporte, la blockchain verrouille

Le build est chiffré une seule fois (AES-256-GCM). La licence est un jeton ERC-721 ; posséder le jeton donne le droit d'obtenir un ticket pour sa machine.

La clé suit la machine, pas le wallet

Un wallet ne sait pas déchiffrer. La clé de contenu est enveloppée (ECIES) pour une clé d'appareil rangée dans le coffre Windows ; le wallet ne fait que signer l'autorisation.

Contrôle hybride

En ligne : ownerOf / userOf en direct (révocation immédiate, toutes les 20 s en partie). Hors ligne : signature plateforme + expiration (30 jours).

Le clair reste dans Rust

Le déchiffrement se fait dans le cœur Rust du launcher ; un jeu web est servi depuis la mémoire, un jeu natif n'existe sur disque que pendant la partie.

Vérification de propriété, pas DRM

Sans puce sécurisée, un utilisateur technique peut extraire une copie avant de revendre. C'est assumé et dit (section 9).

Services sans état

Depuis le 11 octobre, ticketd garde le durable dans Postgres et le jetable dans Redis : il tourne en plusieurs réplicas. SQLite + mémoire restent le défaut en local.

3. Vue d'ensemble

Trois canaux relient les pièces : HTTP (launcher et site vers ticketd), transactions et lectures sur la blockchain (site, launcher, ticketd), et fichiers sur la cartouche et dans la bibliothèque du PC. Le launcher ouvre les pages du site pour tout ce qui exige le wallet (acheter, appairer, revendre, prêter).

Schéma Postgres / SQLite

Une seule interface SQL asynchrone (ticketd/src/sql.ts) sert les deux moteurs ; les dépôts de ticketd/src/db.ts écrivent du SQL portable. Le schéma évolue par migrations numérotées (MIGRATIONS, table schema_migrations), appliquées au démarrage sous verrou consultatif : avec plusieurs réplicas, une seule les applique. On ajoute une migration, on ne modifie jamais une migration appliquée. Horodatages en millisecondes (BIGINT sous Postgres), binaires en BLOB / BYTEA.

TableContenuMigration
content_keysCID, clé chiffrée (nonce ‖ AES-GCM, CID en donnée associée), wallet et studio de publication1

friend_requests, friendshipsdemandes en attente ; amitiés (paire triée) et date de début1
profilespseudo, bio, type d'avatar, favoris (JSON), dates1
avatarsimage de l'avatar (partagée par tous les réplicas)2
playstatssecondes jouées par adresse et édition1

Atomicité entre réplicas : tx(fn, lockKey) prend un verrou consultatif Postgres de transaction sur une clé métier (le wallet, la paire d'amis). Il garantit les plafonds : 2 appareils, 16 amis (500 pour un studio), 50 souhaits. Sous SQLite, toutes les instructions passent par une seule connexion sérialisée.

Outils : npm run migrate -w @gamevault/ticketd (appliquer, --status, --from-sqlite : copie complète SQLite → Postgres en une transaction, après avoir vérifié que la clé maître déchiffre les clés de la source) ; npm run backup (copie SQLite ou pg_dump).

Cartouche et bibliothèque

La carte est la clé ; le jeu s'installe par défaut dans un dossier du PC, ou sur la carte si elle a la place. Sans carte insérée, on ne joue pas.

E:\gamevault\ ├── ticket.json dernier ticket écrit (sert à la détection de la carte) ├── tickets\ │ └── <clé d'appareil>.json un ticket par machine appairée (2 gardés) ├── meta.json titre, studio, édition (affichage) └── build.enc facultatif : le jeu sur la carte D:\GameVault\ bibliothèque PC (proposée à la création) └── Stress Test 500 (QmTJ6tfc)\ ├── build.enc le jeu chiffré, vérifié ├── gamevault.json identité du dossier (CID, titre, édition) ├── build.enc.part téléchargement en cours (reprise) ├── build.enc.dl.json état des morceaux └── build.enc.manifest.json liste des morceaux (réparation hors ligne)

Détection : tout volume amovible qui contient /gamevault/ticket.json (Rust, sysinfo, launcher/src-tauri/src/media.rs). Le ticket porte tokenId, contract, chainId, ownerAddress, devicePubKey, wrappedContentKey, issuedAt, expiresAt et la signature plateforme sur le SHA-256 d'un JSON canonique (shared/src/ticket.ts, miroir Rust ticket.rs). build.enc = nonce 12 octets ‖ données ‖ tag GCM, identique pour toutes les copies.

7. Flux

Publication d'un build

  1. studioChoisit le fichier (.html ou .exe, reconnu par « MZ ») ; le navigateur calcule son SHA-256 et fait signer le message « GameVault Publish ».web/app/studio/page.tsx · publishEdition
  2. ticketdVérifie signature, âge, nonce, hash et propriété du studio on-chain ; génère une clé aléatoire, chiffre, épingle sur IPFS, garde la clé chiffrée et une copie du build en cache.POST /publish · service.ts · publishBuild
  3. studioCrée l'édition on-chain avec prix, stock, revente oui/non, redevance et le couple CID + hash.GameRegistry.createEdition

La clé est liée au studio qui a publié et à la première édition qui référence ce CID (une autre édition ne peut pas obtenir de ticket pour ce build).

Appairage d'une machine

Lancement d'un jeu

  1. launcherPLAY n'est actif que si la carte est authentique (forme, chaîne, signature, expiration, machine) et le build présent (carte ou bibliothèque).judge · isOurs · playableNow
  2. launcherEn ligne (2 s) : ownerOf / userOf ; pendant un prêt seul l'emprunteur joue. Puis : cet appareil est-il encore actif ? Hors ligne : fenêtre de 30 jours.checkOwnerOnline · deviceStillActive
  3. cœur RustRevérifie tout le ticket (contrat lu à la compilation dans deployments.ts), lit la clé d'appareil, déballe la clé de contenu, déchiffre en mémoire, libère aussitôt le chiffré.play_game · ticket.rs · crypto.rs
  4. cœur RustWeb : HTML servi depuis la mémoire par game://. Natif : exe écrit dans %LOCALAPPDATA%\GameVault\run\…, empreinte revérifiée en flux, lancé et surveillé ; dossier effacé à la fin.lib.rs · launch_native
  5. launcherPendant la partie, contrôle en ligne toutes les 20 s : revente ou appareil déconnecté → partie coupée (ERR 0x52 / 0x53).startSessionWatchdog

Téléchargement par morceaux et réparation

  1. launcherDemande la liste des morceaux à ticketd : morceaux de 4 Mio, SHA-256 de chacun, SHA-256 global = l'empreinte inscrite on-chain.GET /build/:cid/manifest · download.rs · load_manifest
  2. cœur Rust4 workers en parallèle, plages HTTP : ticketd d'abord, passerelles IPFS (Pinata, ipfs.io, dweb.link) en secours, morceau par morceau. Chaque morceau est vérifié à l'arrivée ; état persisté (reprise après pause ou redémarrage).fetch_chunks · fetch_range
  3. cœur RustLimite de vitesse par seau à jetons partagé ; pause automatique pendant une partie (option) ; empreinte finale comparée à la valeur on-chain, la racine de confiance.throttle · set_limit
  4. ticketdSert les plages en flux depuis son disque (jamais le fichier entier en mémoire) et calcule la liste des morceaux en flux.server.ts · /build · service.ts · getBuildManifest
  5. launcherVÉRIFIER relit les morceaux, ne retélécharge que les abîmés, puis revérifie l'empreinte finale.run_repair

Vérifié sur le build de 480 Mio : 121 morceaux, pause et reprise, 3 morceaux abîmés réparés exactement, 2 morceaux réparés via IPFS avec le serveur coupé.

Revente et révocation

Temps réel avec plusieurs réplicas

Un flux SSE (GET /events?token=) est tenu par le réplica qui l'a accepté. Un événement (message, lecture, présence, amis) est publié sur le canal Redis gv:events ; chaque réplica le reçoit et le remet aux flux qu'il tient pour ce wallet. Sans Redis, la remise se fait en mémoire (un seul processus). À l'arrêt d'un réplica, ses flux sont fermés et les clients se reconnectent ailleurs.

9. Sécurité

Garanti

  • Le wallet ne signe que dans le navigateur ; sa clé privée n'atteint ni le launcher, ni la carte, ni ticketd.
  • Un ticket est scellé pour une machine : copier la carte ne sert à rien sans la clé d'appareil.
  • Le ticket est vérifié en TypeScript puis dans Rust avant tout déchiffrement ; un ticket d'un autre déploiement du contrat est refusé.
  • Le clair reste en mémoire (jeu web) ou n'existe que pendant la partie (jeu natif, empreinte revérifiée).
  • En ligne, revente et prêt révoquent l'ancien détenteur au lancement et en partie (20 s).
  • Messages signés non rejouables, même après redémarrage et même sur un autre réplica (nonces en base).
  • Téléchargements : chaque morceau vérifié, empreinte finale comparée à la valeur on-chain ; un serveur ou un miroir menteur est toujours détecté.
  • Clés de contenu chiffrées au repos ; une clé par rôle ; aucun destinataire ne peut bloquer une revente.
  • Infra : conteneurs non-root, lecture seule, Pod Security « restricted », NetworkPolicy, limites de débit par IP, TLS, secrets hors du dépôt et des images.

Limites assumées

  • Copie déchiffrée : un utilisateur technique peut extraire la clé avant de revendre. « Vérification de propriété, pas DRM ».
  • Fenêtre hors ligne : un vendeur resté hors ligne joue jusqu'à 30 jours après la vente.
  • ticketd est un tiers de confiance : il détient les clés de contenu et la clé des tickets.
  • Chat non chiffré de bout en bout ; une session volée permet des actions sociales pendant 24 h.
  • Exe natifs non signés (Authenticode pas encore vérifié).
